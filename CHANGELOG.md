# Changelog

## Unreleased

RDF 1.2/SPARQL 1.2 conformance hardening since 0.1.0:

- **RDF 1.2 VERSION-directive conformance checking** (`RDF12ConformanceWarning`) across Turtle, N-Triples, N-Quads, TriG, RDF/XML, SPARQL, and the native `rdf-1.2` backend.
- **Full W3C conformance** — the Turtle 1.2 test suite went from 29 to 103 tests (added the syntax-conformance cases alongside eval), which surfaced and fixed real gaps: stricter `TurtleSyntaxError` handling, predicate/subject position validation for triple terms and reified triples, annotation-block arity, VERSION directive grammar, base-direction case sensitivity, and surrogate-escape rejection.
- **`isomorphic()`** now correctly handles TripleTerms containing blank nodes, and is more rigorous generally (was previously using rdflib's own approximate check).
- Fixed several SPARQL 1.2→1.1 rewriter bugs (WHERE-less queries, bare `TRIPLE()` in a SELECT projection, nested `isTRIPLE()`).
- Adopted Apache Jena's real TriX convention; fixed an RDF/XML `rdf:version` data-corruption bug.
- Removed the obsolete `rdf-star` backend mode (superseded by `rdf-1.2`).
- Assorted smaller fixes: `tt:HASH` collision risk, the `sqlalchemy` extra failing to install on a fresh environment, query/update state leaking across calls.
- **Performance: `StarlightGraph.query()`/`StarlightDataset.query()` no longer re-rewrite and re-parse the same query text on every call.** Callers that evaluate the same query repeatedly with only `initBindings` differing — the exact pattern used by SHACL-AF `sh:construct` rules and `sh:sparql` constraints, evaluated once per focus node — now hit a per-instance prepared-query cache (`starlight.query.query_cache.prepare_query_cached`, keyed on query text + effective namespaces + base IRI) instead of redoing the SPARQL 1.2→1.1 rewrite and rdflib's own SPARQL parse every time. ~4.5x faster per repeated call in a microbenchmark; the win scales with how many times a query is re-evaluated per unmutated graph, which for rule-heavy validations grows with graph size. **Follow-up fix**: the cache initially assumed passing a pre-parsed `Query` object to `Graph.query()` was safe for any store (a documented rdflib capability in the general case) — confirmed via real Fuseki testing that `rdflib.plugins.stores.sparqlstore.SPARQLStore`/`SPARQLUpdateStore` (used for *any* remote HTTP SPARQL endpoint, not just Fuseki) hard-require a plain string and raised `AssertionError` otherwise. `StarlightGraph.query()` now checks `starlight.query.query_cache.store_accepts_prepared_query` and falls back to a plain rewritten string for these stores — no regression, and no lost benefit either, since these stores forward the query text to a remote server, so local rdflib-side re-parsing was never the bottleneck there. `StarlightDataset.query()` was never affected (it always executes against its own always-in-memory `_build_raw_execution_graph()`, regardless of the dataset's own backing store).
- **Fixed: `StarlightGraph.parse(format='turtle12'/'longturtle12'/'trig12')` on a native (`backend='rdf-1.2'`) graph wrote the rdf-1.1 backend's own tt:HASH skolemized encoding directly into the store, for *any* backend.** These three parse branches called `super().add(triple)` (rdflib's base `Graph.add()`), bypassing the backend-aware `StarlightGraph.add()` override that routes triple-term values to `_native_add()` for real `<<( )>>` storage - so a triple term parsed from text (as opposed to added via the `.add()` Python API, which was never affected) never decoded correctly on a native-backend graph: `.triples()` returned the raw `rdf:subject`/`rdf:predicate`/`rdf:object` encoding fragments instead of a `TripleTerm` object, and `rdf:reifies` lookups against such data never matched. Confirmed to affect both simple and nested triple terms. Fixed by decoding the skolemized encoding back into real `TripleTerm` objects (`starlight.parsers.turtle_parser.decode_tt_encoded_triples`) before writing native-backend data, so it goes through `self.add()` → `_native_add()` instead; the rdf-1.1 backend path is untouched (its tt:HASH encoding *is* that backend's own on-disk representation, so writing it directly was always correct there). Found via a downstream consumer's `sh:reifierShape`/`sh:reificationRequired` breaking end-to-end against a live Oxigraph backend.
- **Fixed: same bug, separate code path — `StarlightDataset.parse(format='trig12')` on a native-backend dataset had the identical problem.** Its per-context write loop called the module-level `_raw_graph_add` (rdflib's base `Graph.add()`, aliased at import time) unconditionally regardless of backend, never routing through the per-context `StarlightGraph.add()` override. This is a distinct implementation from `StarlightGraph.parse()`'s trig12 branch (the dataset builds one context per named graph via `parse_trig12_named()`, rather than merging all graphs into one via `parse_trig12()`), so fixing the graph-level path did not fix this one. Confirmed via real Oxigraph *and* Fuseki testing: a triple term parsed into a named graph never came back as a `TripleTerm` from `ds.get_context(...).triples()`. Fixed the same way — decode the tt:HASH encoding back into real `TripleTerm` objects before writing, per named-graph context, only on the native-backend path; the rdf-1.1 backend path (`_raw_graph_add` + `_build_registry_from_store()`) is untouched.
- **Fixed: `StarlightDataset.query()` had no native-backend (`rdf-1.2`) dispatch at all, and crashed with `TypeError: unknown binding type` on any query result containing a triple-term-valued binding** (e.g. `SELECT ?tt WHERE { GRAPH ?g { ?s rdf:reifies ?tt } }`). Unlike `StarlightGraph.query()`, which routed to its own native-only query logic for `self._is_native`, `StarlightDataset.query()` always queried a plain in-memory copy built by `_build_raw_execution_graph()` — for a native-backend context, that copy is built by reading through rdflib's base `Graph.triples()` (a plain SPARQL 1.1 `SELECT ?s ?p ?o` against the remote store), which cannot represent a `"type":"triple"` JSON binding. Plain-triple dataset queries were unaffected; only triple-term-valued results crashed. Fixed by giving `StarlightDataset` the same native-backend query dispatch as `StarlightGraph` (a native-backed dataset's per-context graphs all share one store, so cross-graph queries are the same underlying HTTP operation — graph scoping comes entirely from the query's own `GRAPH` clauses, same as the single-graph path). Confirmed via real Oxigraph and Fuseki testing for SELECT, ASK, and CONSTRUCT.
- **Fixed: `StarlightDataset.update()` crashed with `HTTP 400` on any update text containing its own `GRAPH <uri> { }` clause, against a remote store on *both* backends** — not a triple-term bug at all, but an rdflib/`SPARQLStore` quirk: `Dataset(store=...).update()` always wraps the whole update text in an extra `GRAPH <urn:x-rdflib:default> { }` block (`SPARQLStore._is_contextual()` doesn't recognize `Dataset`'s own default-graph sentinel — a `URIRef`, which subclasses `str` — as exempt from wrapping; only the literal string `"__UNION__"` is special-cased), nesting illegally around any update that already has its own `GRAPH` clause, which is the normal way to target a named graph from dataset-level SPARQL. Confirmed via real Oxigraph and Fuseki testing with a plain `INSERT DATA { GRAPH <uri> {...} }` containing no triple terms at all. Fixed by bypassing rdflib's `Dataset.update()` dispatch and sending the update over HTTP directly for any store with query/update endpoints, for both backends (rdf-1.2 unmodified, rdf-1.1 still rewritten to the tt:HASH encoding first).
- **Refactor: deduplicated `StarlightGraph`'s and `StarlightDataset`'s native-backend (`rdf-1.2`) dispatch logic into shared functions in `starlight.backends.native`** (`resolve_store_http`, `check_native_version_conformance`, `native_query`, `native_update`), rather than each class carrying its own near-identical copy. This is what let the query/update bugs above exist in the first place — a fix landing in one class's copy had no way to reach the other's. Both classes' `.query()`/`.update()` now call the same functions; `StarlightGraph._native_query()` and `StarlightDataset._native_query()` no longer exist as separate methods. No behavior change beyond the two fixes above; confirmed via the full integration suite against real Oxigraph and Fuseki.
- **Fixed: `StarlightGraph.from_rdflib(some_dataset)` crashed with `ValueError: too many values to unpack (expected 3, got 4)`** on any `Dataset`/`ConjunctiveGraph` input. The internal `turtle_parser._skolemize_encoding()` helper it calls did bare `for s, p, o in g:` iteration, which assumes `g` is triple-shaped; a `Dataset` yields 4-tuples `(s, p, o, context)` from `__iter__`. Fixed by reading via `g.triples((None, None, None))` instead — the same call `Graph.__iter__` itself delegates to, so behavior for a plain `Graph` is unchanged, but for a `Dataset` it correctly returns 3-tuples and — importantly — respects whatever `default_union` the dataset was constructed with (rdflib default: `False`), rather than crashing or silently unioning every named graph regardless of that setting. A `Dataset(default_union=False)` (the default, and what `StarlightDataset` itself uses) now copies only the default graph into the resulting `StarlightGraph`, matching the dataset's own declared semantics; `default_union=True` copies everything, same as iterating the dataset directly would.
- **Fixed: `StarlightDataset.triples()` ignored `default_union` entirely and always returned the union of every named graph**, contradicting its own documented default-graph-isolation contract (`default_union=False` is the class's stated default, matching plain rdflib `Dataset`). Found while verifying the `from_rdflib()` fix above: that fix relies on the source dataset's `.triples()` correctly respecting `default_union`, which plain `rdflib.Dataset` does but `StarlightDataset` did not — so a `StarlightDataset(default_union=False)` (the default) still leaked named-graph content through `from_rdflib()` despite the fix. Fixed by making `triples()` branch on `self.default_union`: `True` keeps the existing behavior (union via `quads()`); `False` now delegates to the default graph's own `StarlightGraph.triples()` only (TT restoration and encoding-triple filtering still apply either way). `tests/unit/test_dataset.py::TestQuads::test_triples_union_view` was itself asserting the buggy union-regardless-of-flag behavior against a default-constructed (`default_union=False`) dataset; updated to construct with `default_union=True` explicitly, plus a new `test_triples_default_union_false_excludes_named_graphs` covering the correct default behavior.
- **Fixed: same `default_union` propagation gap, two more places — `StarlightDataset.query()` and `.update()` silently ignored `default_union=True`.** Both build their own internal `Dataset` wrapper to execute against (`_build_raw_execution_graph()` for `.query()`'s in-memory-backend path; a `Dataset(store=self.store)` for `.update()`'s), and both constructed it with rdflib's default (`default_union=False`) regardless of `self.default_union` — so on a `StarlightDataset(default_union=True)`, a GRAPH-less `SELECT`/`WHERE` pattern silently matched nothing from any named graph instead of seeing their union, exactly the `.triples()` bug above but two more call sites. Fixed by forwarding `default_union=self.default_union` to both. (A GRAPH-less `INSERT`/`DELETE` template still targets the dataset's own default graph either way — `default_union` only widens what a GRAPH-less `WHERE` can match, not where an update writes to; confirmed this matches plain `rdflib.Dataset`'s own behavior exactly, not a Starlight-specific quirk.) New `TestDefaultUnionPropagation` test class in `tests/unit/test_dataset.py` exercises `default_union` across `.query()` and `.update()` together, alongside the existing `.triples()` coverage, rather than one-off tests per bug found.
- **Fixed 4 Turtle 1.2 parsing bugs found via a downstream consumer running the real-world W3C SHACL 1.2 test suite through `format='turtle12'`** (this suite is not part of this repo - see the downstream project's own test-suite-integration docs):
  - **`next_token()`'s plain-token fallback only stopped at whitespace or `<`**, so a token immediately followed by `(`, `[`, `{`, `"`, `'`, `,`, or `;` with no separating space (e.g. `sh:resultPath(...)`, valid Turtle - none of these characters can appear inside a PrefixedName/IRI token, so no space is needed to disambiguate) glued the delimiter onto the preceding token instead of starting a new one. Widened the fallback scan's stop-character set (`starlight/parsers/lexer.py`).
  - **RDF collection (`( ... )`) members never got the same bare-literal string→Python-value coercion (`coerce_object()`) an ordinary (non-list) object already receives in `extract_fields()`** - a collection containing a bare numeric/boolean literal (e.g. `( 42 )`, `( true false )`) reached final term conversion as a raw string and was rejected as an "unrecognized term" (`_to_node()` already handles Python `bool`/`int`/`float` correctly; it just never received them for list members). Fixed by calling `coerce_object()` on each collection element in `expand_triple_set()` (`starlight/parsers/syntax.py`) - safe unconditionally, since a bracket/quote-wrapped member never matches `coerce_object`'s literal patterns.
  - **A `#` comment starting after other content on the same line was never stripped** - only a comment occupying a *whole* line was recognized (a pre-filter in `StarlightTurtleParser.parse()`). Fed the trailing comment text into the grammar as if it were real content, producing spurious "unexpected trailing content" errors. Fixed by stripping `#`-to-end-of-line directly in the statement-splitting/directive-scanning character loops (`_split_statements_impl`/`_scan_directive_end` in `starlight/parsers/syntax.py`), gated on not being inside a string or an `<IRI>` (which may legitimately contain a literal `#` fragment).
  - **`StarlightGraph.parse(location=..., format='turtle12', publicID=...)` never resolved relative IRIs (including a bare `<>`) against `publicID`** - `StarlightTurtleParser.parse()` had no parameter to accept a seed base at all; only an in-document `@base`/`BASE` directive ever set `current_base`. Fixed by adding a `base` parameter to `StarlightTurtleParser.parse()` (seeds `current_base`; an in-document `@base` still overrides it from that point on, `urljoin`'d against it exactly as a second `@base` would be) and having `StarlightGraph.parse()`'s `turtle12`/`longturtle12` branch pass `publicID`, falling back to `location`'s own resolved `file://` IRI when `publicID` isn't given - matching the convention rdflib's own parsers follow.

  New regression coverage: `tests/unit/test_turtle_parser.py`'s `TestNoSpaceBeforeDelimiter`, `TestCollectionElementLiteralCoercion`, `TestMidLineComments` classes, and three new cases in `TestBaseURI` (all 11 confirmed to fail against the pre-fix code, not just pass against the fix).
- **Fixed: ECHAR escapes `\b`/`\f` (backspace/form-feed) never decoded in string literals** — `turtle_parser._unescape()` and `ntriples12._unescape_nt()` both handled the full RDF 1.1/1.2 ECHAR table except these two, silently leaving the literal two-character text `\b`/`\f` in the decoded string instead of the real control characters (U+0008/U+000C) the grammar defines them as. Found via a downstream consumer's `sh:singleLine` fixture, which needs a real form-feed to trigger. New coverage: `tests/unit/test_turtle_parser.py::TestPlainTurtle::test_form_feed_and_backspace_escapes_decode`, and a new `tests/unit/test_ntriples12.py` (previously zero coverage for this parser).
- **Fixed: `algebra_translator_patches.py`'s own `"Extend"`-branch fix (see `docs/rdflib-upstream-issues.md` Issue 4) regressed `GROUP BY` queries that project a grouped variable directly** — rdflib's implicit-`SAMPLE`-wrapping bookkeeping (`Variable('__agg_N__')`) got rendered as a literal, illegal in-pattern `BIND(SAMPLE(?p) AS ?p)` instead of being collapsed into the `SELECT`-list the way stock rdflib's own (unpatched) logic does. Found via the downstream `sparql1.2_to_rdf` project's adversarial round-trip tests. Fixed by falling through to the original `sparql_query_text` specifically for an `Extend` whose `expr` is one of these synthetic aggregate-result variables. See `docs/rdflib-upstream-issues.md` Issue 4's addendum for the full root-cause writeup.
- **Patched a confirmed plain-rdflib bug: `translateAlgebra` drops the `*` for `SELECT * WHERE { <fully-ground pattern> }`** (a WHERE clause with zero variables anywhere — an unusual but valid "does this fact exist" query), regenerating invalid, unparseable `SELECT {...}` text instead. Also found via the downstream `sparql1.2_to_rdf` project's adversarial round-trip tests; unrelated to RDF 1.2/triple terms. See `docs/rdflib-upstream-issues.md` Issue 7.
- **Fixed: `native.py`'s SPARQL JSON result parser (`_parse_json_term`) crashed with an unhandled, confusing double-fault when a native backend's query result contained a `"triple"` binding whose own subject was itself a triple term** — not valid RDF 1.2 (a triple term's subject may never itself be a triple term), and something a spec-conformant engine should never actually return, but confirmed a real Fuseki 5.5.0 bug can produce it in practice (`TRIPLE(subject, ...)` fails to validate a triple-term-valued `subject` the way it already validates `predicate` — see `docs/fuseki-upstream-issues.md` Issue 1). `TripleTerm.__init__`'s own validation correctly rejected constructing it, but raised *before* assigning any of its `__slots__`, so anything that tried to `repr()`/`str()` the half-constructed instance afterward (traceback formatting, notably) hit a *second*, unrelated `AttributeError`, obscuring the real problem. Fixed two ways: `_parse_json_term` now catches this specific `ValueError` and re-raises one clear, single error identifying the actual cause (a native-engine conformance issue, not a bug in this library) instead of letting the raw exception propagate into the double-fault; separately, `TripleTerm.__str__`/`__repr__` are now defensive against a half-constructed instance regardless of cause, so this class of secondary crash can't recur even from an unrelated future failure path.
- **Documented (`xfail(strict=True)`, not fixed) 4 known in-memory-backend-specific limitations in the W3C SPARQL 1.2 eval suite: `op-2`, `order-1`, `order-2`, `construct-5`.** Confirmed all 4 are specific to the in-memory (`rdf-1.1`, `tt:HASH` content-addressed URI encoding + SPARQL 1.2→1.1 text rewrite) backend, not a gap in RDF 1.2/SPARQL 1.2 support generally — the native (Oxigraph) backend already passes all 4 cleanly with zero query rewriting (`op-2` has its own separate, narrower, already-documented Oxigraph decimal-lexical-form quirk instead). Root cause for `op-2`/`order-1`/`order-2`: a triple term is stored as an opaque, content-addressed `tt:HASH` URI, so stock rdflib's `=`/`sameTerm` operators and `ORDER BY` comparator have no way to apply RDF 1.2's own value-equality/term-kind-ordering semantics to it — fixing either would mean overriding rdflib's comparison/sort internals, used throughout the evaluator, for a rewrite pipeline `docs/rdflib-upstream-issues.md` already documents as intended to be superseded by the SPARQL 1.2→algebra→regenerate pipeline routing to a native backend, so not attempted. `construct-5` is narrower: `CONSTRUCT WHERE`'s annotation-shorthand rewriter reuses one reifier identity for both WHERE-matching and CONSTRUCT-template instantiation instead of minting a fresh one for the template's own re-assertion (ordinary CONSTRUCT semantics for an otherwise-unbound template blank node) — also not attempted, same reasoning. See the new `_IN_MEMORY_KNOWN_DIVERGENCES` table in `tests/w3c_sparql12/test_w3c_sparql12_eval.py` for the full per-test writeup.
- **Patched 2 confirmed bugs in plain rdflib's own SPARQL arithmetic evaluation** (`rdflib.plugins.sparql.operators`, not this repo's own code) — found via the same downstream W3C SHACL 1.2 test suite run, reproduced independently with a bare `rdflib.Graph().query()`: (1) `MultiplicativeExpression` (`*`/`/`) never applies SPARQL 1.1's numeric type-promotion rules the way `AdditiveExpression` (`+`/`-`) already does, so `xsd:integer * xsd:integer` always comes back `xsd:decimal`; (2) `Builtin_CEIL`/`Builtin_FLOOR`/`Builtin_ROUND`, and whole-number division results, correctly keep the `xsd:decimal` datatype but lose the canonical `.0` lexical form (e.g. `ceil(3.2)` → `"4"`, not `"4.0"`). New `starlight/query/operator_patches.py`, applied eagerly from `starlight/__init__.py` so every consumer gets spec-correct results — mutates the relevant `Comp` grammar-node objects inside rdflib's already-built pyparsing SPARQL grammar (a mutable instance attribute read fresh on every parse, not a closure baked in at import time), rather than touching any installed rdflib file. New `tests/unit/test_operator_patches.py` (10 tests, confirmed to fail via `git stash` against the pre-patch code).

## 0.1.0 — 2026-05-14

Initial public release.

### Features

- **`StarlightGraph`** — drop-in replacement for `rdflib.Graph` with full RDF 1.2 support
- **Triple terms** — `TripleTerm` objects as first-class Python values; content-addressed internal encoding (`tt:HASH`)
- **All annotation forms** — parses and serializes `{| |}`, `~ :r`, `<<( )>>`, and `<< >>` syntax
- **SPARQL 1.2** — triple-term patterns rewritten to SPARQL 1.1 for `rdflib` compatibility; `isTripleTerm()`, `SUBJECT()`, `PREDICATE()`, `OBJECT()` functions supported
- **CONSTRUCT queries** — result graph is a `StarlightGraph` with TripleTerms correctly restored
- **8 serialization formats** — `turtle12`, `longturtle12`, `nt12`, `nq12`, `trig12`, `trix12`, `rdfxml12`, `jsonld12`
- **W3C conformance** — passes the W3C Turtle 1.2 test suite (29 `TestTurtleEval` cases)
- **Multiple backends** — in-memory (default), SQL via `rdflib-sqlalchemy`, Apache Fuseki (`rdf-1.1` and `rdf-star` modes), Oxigraph (`rdf-1.2` native mode)
- **PEP 561** — `py.typed` marker included; package is typed
